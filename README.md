# Astrospect

Astrospect is a Django web application for calculating and exploring birth
charts. It pairs transparent chart calculations with plain-language,
source-grounded explanations generated by a configurable language model.

## What the app does

- Calculates tropical-zodiac placements and whole-sign houses.
- Displays the seven classical planets and the True Node, along with the four
  chart angles when birth time and birthplace are available.
- Lets users expand a placement for a short explanation or ask follow-up
  questions about their chart.
- Uses a small, approved Jyotisha source catalog for the AI guide; model output
  can cite only sources in that catalog.
- Supports optional saved charts and caches generated placement summaries.

Astrospect deliberately presents its use of traditional Jyotisha as a modern
adaptation. The chart uses the tropical zodiac and whole-sign houses; it does
not calculate sidereal placements, nakshatras, or dashas. Traditional Jyotisha
texts do not establish that their authors prescribed tropical astrology, and
the app labels this distinction rather than implying otherwise. Interpretive
text is framed as historical symbolism, not scientific prediction.

## Design choices

### PostgreSQL for application data

The project started with SQLite while the application was being developed.
PostgreSQL is now the configured database because it is a better fit for a
hosted, multi-user Django application:

- It is a client-server database that can be shared by multiple web workers,
  rather than a single local database file.
- It provides durable, managed database options for deployment and avoids
  making production data depend on the web service's local filesystem.
- It gives local development and production the same database behavior,
  reducing surprises when deploying.
- It supports the app's Django models and JSON-backed chart and summary data.

The application does not silently fall back to SQLite. Configure PostgreSQL
with `DATABASE_URL`, or provide the individual `DB_NAME`, `DB_USER`,
`DB_PASSWORD`, `DB_HOST`, and `DB_PORT` settings. `DATABASE_URL` takes
precedence when both forms are present. Django migrations create or update the
schema; they do not automatically copy existing records from an old SQLite
database into PostgreSQL.

### OpenAI-compatible API for model flexibility

The application uses the OpenAI Python SDK's Chat Completions interface, but
that does **not** mean it is locked to OpenAI-hosted models. The SDK supports an
OpenAI-compatible API endpoint, so Astrospect selects its provider, model, and
credential through environment variables rather than hard-coding a provider
into chart or chat code.

The current configuration uses OpenRouter and the free model
`nvidia/nemotron-3.5-lightning:free`. To try another model or compatible
provider, change `AI_BASE_URL`, `AI_API_KEY`, and `AI_MODEL`; the application
code can stay the same as long as the provider supports the Chat Completions
API used here. Model availability, free-tier limits, output quality, and
provider-specific behavior can change, so check the provider's current model
listing before switching.

The selected model is asked to follow server-controlled instructions and
return a structured answer. The app validates its response and resolves source
citations against the approved catalog instead of trusting model-generated
source URLs.

## Running locally

### Requirements

- Python and pip
- A PostgreSQL server and a database/user for Astrospect
- An OpenRouter API key and a model that supports the compatible API, if you
  want live AI responses
- A Geoapify API key, if users should be able to look up birthplaces

### Install and configure

From the project directory, create and activate a virtual environment, then
install dependencies:

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

Create a `.env` file in the project root. For example:

```text
# PostgreSQL connection. Use either DATABASE_URL or the DB_* values below.
DATABASE_URL=postgresql://astrospect:your-password@localhost:5432/astrospect

# OpenRouter's OpenAI-compatible API
AI_API_KEY=your_openrouter_api_key
AI_BASE_URL=https://openrouter.ai/api/v1
AI_MODEL=nvidia/nemotron-3.5-lightning:free
AI_TIMEOUT_SECONDS=60

# Optional: Geoapify birthplace lookup
GEOAPIFY_API_KEY=your_geoapify_api_key

# Local Django settings
DJANGO_DEBUG=True
DJANGO_SECRET_KEY=replace-this-for-local-development
DJANGO_ALLOWED_HOSTS=localhost,127.0.0.1
```

Keep `.env` private; it is excluded from Git. Never put API keys or production
secrets in source files or commit them to the repository.

If you prefer separate PostgreSQL connection settings, omit `DATABASE_URL` and
set all of the following instead:

```text
DB_NAME=astrospect
DB_USER=astrospect
DB_PASSWORD=your-password
DB_HOST=localhost
DB_PORT=5432
```

The `.env` file is optional for Django itself, but AI and geocoding features
need their corresponding provider settings. Without an AI key or model, live
inference is not available.

Apply database migrations and start the development server:

```powershell
python manage.py migrate
python manage.py runserver
```

Open `http://127.0.0.1:8000/` in a browser. Django's default development
server is for local development, not production hosting.

## Configuration reference

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL` | PostgreSQL connection URL; takes precedence over individual `DB_*` values. |
| `DB_NAME` | PostgreSQL database name when `DATABASE_URL` is unset. |
| `DB_USER` | PostgreSQL user when `DATABASE_URL` is unset. |
| `DB_PASSWORD` | PostgreSQL password when `DATABASE_URL` is unset. |
| `DB_HOST` | PostgreSQL host when `DATABASE_URL` is unset. |
| `DB_PORT` | PostgreSQL port when `DATABASE_URL` is unset. |
| `AI_API_KEY` | Secret key for the selected OpenAI-compatible provider. |
| `AI_BASE_URL` | Provider's API base URL; OpenRouter uses `https://openrouter.ai/api/v1`. |
| `AI_MODEL` | Model identifier recognized by the selected provider. |
| `AI_TIMEOUT_SECONDS` | Maximum request time for model calls; defaults to 60 seconds. |
| `GEOAPIFY_API_KEY` | Optional key used for birthplace search and timezone lookup. |
| `DJANGO_SECRET_KEY` | Django signing and session secret; use a strong private value in production. |
| `DJANGO_DEBUG` | Enables Django debug mode; set to `False` in production. |
| `DJANGO_ALLOWED_HOSTS` | Comma-separated hostnames Django may serve. |

Use provider-specific credentials with `AI_API_KEY`. For OpenRouter, create a
key in your OpenRouter account; for a different compatible provider, use that
provider's key, base URL, and model identifier. The key stays on the server and
is not sent to the browser.

## Chart inputs and interpretation

- A birth time without a selected birthplace is treated as a UTC approximation
  for planetary positions. Houses and angles require both a birthplace and
  birth time.
- If no birth time is supplied, the app cannot determine houses or angles.
- Without a birthplace, the app checks whether a planet could have changed
  signs during that UTC date and flags uncertain placements.
- Planet sign conditions such as own sign, exaltation, or debilitation are
  kept distinct from house placement. Angular houses (1st, 4th, 7th, and 10th)
  are described as a separate kind of prominence.
- Entering a birthplace uses Geoapify to resolve coordinates and timezone;
  chart calculations themselves are performed locally by Kerykeion.

## Saved-chart and AI data

New chart calculations are held in the user's Django session. If the user
chooses the save option, the app stores a chart record in the configured
database so it can be restored using its private saved-chart link. Generated
placement summaries can be cached with that chart. Anyone with a saved link
may be able to open the associated chart; use the delete control on the chart
page to remove it. The chart is not a public profile or a synced browser
account.

Chat requests send the user's question, the chart facts needed to answer it,
approved source information, and up to the eight most recent conversation
messages to the configured model provider. The prompt does not include the
user's name or raw birth location. Review the provider's data-handling terms
before enabling hosted inference with personal chart information.

## Tests and AI connection check

Run the Django tests with:

```powershell
python manage.py test astrospect.tests.tests
```

The test database user must have permission to create a test database. The AI
connection check sends a real request to the configured provider and model:

```powershell
python scripts/check_ai.py
```

Use that script only when the credentials and model are configured and you
intend to make a live provider request. A model marked free may still have
availability limits or change its terms.

## Deployment

`render.yaml` describes a Render web service. For production, configure a
persistent PostgreSQL database and set `DATABASE_URL` to its connection URL.
Also configure `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`, and the AI
environment variables (`AI_API_KEY`, `AI_BASE_URL`, and `AI_MODEL`) in the
hosting dashboard. Set `DJANGO_DEBUG=False`. Add `GEOAPIFY_API_KEY` if hosted
birthplace lookup should be enabled.

Run the configured build and start commands from the Blueprint:

```text
python manage.py collectstatic --no-input && python manage.py migrate
gunicorn config.wsgi:application
```

The Render build runs `collectstatic`, which gathers the app's assets into
`STATIC_ROOT` (`staticfiles/`). WhiteNoise is installed in the project
dependencies and its middleware is placed immediately after Django's
`SecurityMiddleware`. In production, Django's compressed manifest storage
creates versioned static asset names, and WhiteNoise serves those collected
files at `/static/` directly from the web service. No separate static site,
CDN, or Render static-file service is required. Keep `STATIC_URL` as an
absolute `/static/` path so asset links work from nested application routes.

Render provides an `onrender.com` subdomain and managed HTTPS for its web
services. Keep database and provider credentials in the hosting provider's
environment settings, never in `render.yaml` or Git. Free hosting and free
model tiers can have resource, availability, and rate limits. A custom
registrable domain is not normally free; if you add one, configure it through
the host and use its managed TLS certificate.
